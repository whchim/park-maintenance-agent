# 通义千问接入与验收

## 本轮实际交付

企服报修信息检查、招商意向草稿和工程委派建议已有可配置的千问调用入口。默认仍为离线规则模式；只有显式设置 `PARK_AI_MODE=qwen`，并提供有效的百炼配置，才会请求模型。

当前企服流程与工程建议已接入 LangGraph 1.2.19：企服按完整性进入补项或人工确认分支；工程可由模型选择只读工具、读取结果后形成建议。2026-11-01 已用真实 `qwen3.7-flash` 通过三项固定模拟资料检查，证据见 [真实千问验收报告](./verification/20261101-Qwen验收报告.md)。招商仍为一次结构化模型任务，Supervisor 部门路由仍是确定性业务规则，尚非全平台自主多 Agent；有限用例通过不代表整体质量评测完成。架构依据见 [ADR-001](./architecture/ADR-001-LangGraph.md)。

| 部门 | 千问处理什么 | 后端与人工保留什么 |
|---|---|---|
| 企服 | 提取位置、故障现象和原文依据，生成缺项追问 | 后端重算缺失字段；原始描述保留；优先级由规则提供参考、人工确定；人工确认后才建单 |
| 招商 | 提取客户/联系人/联系方式，建议意向等级和跟进主题 | 提取事实需附原文依据；来源和原文保留；人员核对客户及等级后才建档、创建回访任务 |
| 工程 | 自主选择只读人员目录/当前未结束分派数工具，读回证据后生成委派建议 | 推荐前必须查询目录，只接受有效人员编号；任务数不等于真实负载/值班；负责人自行选择并确认分派 |

签约客户联系单的必填检查仍是确定性规则，没有改为模型审批。模型不判定合同有效性、资料真实性或部门接收结果。

## 本机配置

先在百炼开通可用模型，创建对应地域的 API Key。北京、新加坡等地域的 Key 和入口必须匹配。示例使用 `qwen-plus`，实际以账号已开通模型为准。

本机配置文件是 `backend/.env`，模板是 `backend/.env.example`。本轮已经创建空密钥的本机文件；以后重新下载项目时，可以复制模板建立自己的 `.env`，不要覆盖已有配置。

打开 `backend/.env`，将模式改为 `qwen` 并在本机填入密钥，其他值先保持示例配置：

```dotenv
PARK_AI_MODE=qwen
DASHSCOPE_API_KEY=在本机替换为你的百炼密钥
QWEN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
QWEN_MODEL=qwen-plus
QWEN_TIMEOUT_SECONDS=15
```

密钥只填写到 `.env`，不要写入 `.env.example` 或发到聊天中。文件已被项目 `.gitignore` 排除。初始模式为 `rule`、密钥为空，尚未填写时不会产生模型调用。

停止旧后端后重新启动即可自动加载：

```powershell
Set-Location 'D:\桌面\park-maintenance-agent\backend'
& ..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

后端在导入 `app` 时从固定的 `backend/.env` 加载一次，不受启动目录影响。修改文件后需要重启后端；终端或部署环境中已有的同名变量优先于文件，避免覆盖部署配置。如果之前手动设置过 `$env:PARK_AI_MODE` 等变量，请在新的终端启动，或先清除这些旧变量。

配置加载使用 `python-dotenv`，已加入 `backend/requirements.txt`；当前项目虚拟环境中已有该依赖。新环境安装后端依赖可执行 `..\.venv\Scripts\python.exe -m pip install -r requirements.txt`。`.env` 也预留了飞书 Token 和 Encrypt Key 的空配置，暂时无需填写。

官方现推荐使用业务空间专属入口，例如 `https://你的业务空间ID.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`；上面的北京旧入口在当前官方文档中仍受支持。其他地域请复制百炼控制台提供的官方入口，不要把北京 Key 用于其他地域。代码只接受百炼官方 HTTPS 域名，不跟随重定向发送密钥。

恢复离线演示：将 `.env` 中的 `PARK_AI_MODE` 改为 `rule` 后重启；如果终端中已有同名变量，也需同步调整或清除。

## 由用户参与的验收

1. 打开后端 `/docs`，调用 `GET /api/v1/agents/runtime`。`ready=true` 只证明配置齐全，`connectivity_verified=false` 表示该接口不进行远端探测。该接口不消耗模型请求，不会读取或汇总独立验收报告；实际在线证据以具体调用结果和报告为准。
2. **先做不写数据库的验证：** 调用 `POST /api/v1/repairs/parse`，请求体为 `{"text":"A栋302的顶灯忽明忽暗，请安排检查"}`。成功应返回 `mode=llm`、`ai.model`、耗时、Token 用量和提取依据；模式为 `rule_fallback_demo` 时，按 `ai.fallback_reason` 检查配置或调用故障。
3. 打开“企服报修协同”，先输入“想报修”，再按追问分两次补充“位置在A栋302”“顶灯忽明忽暗”。确认前不应产生工单；核对结构化字段，手动确定优先级后再建单。这一步需要现有工作流表已完成先前增量迁移。
4. 招商输入“海星科技的李先生还在比较园区，暂未提供电话”。检查是否保留未知电话，意向等级仍由你核对后确认。草稿解析本身不写客户表。
5. 在待分派工单点击“生成工程委派建议”，展开“协作执行记录”，核对是否真的查询人员目录，以及是否按需查询了当前未结束分派数。成功必须为 `mode=llm`；检查推荐编号属于演示目录。生成建议不会自动选中或分派人员，负责人仍需在下方选择人员并点击分派。如果显示“模型未查询人员依据”“工具或参数未通过校验”，说明已拦截并规则回退，不能当作模型成功。
6. 在独立测试终端使用无效测试 Key 启动后端并重新解析，检查是否显示“鉴权失败，使用规则回退”。不要修改或删除正式 Key 来做故障演示。

页面模式提示以每次返回结果为准；“已配置”不代表“已调用成功”。原文引用检查能阻止部分编造，不能证明语义理解完全准确，也不能代替人员核对。

## 请求与异常边界

- 企服/招商每个模型任务最多调用一次；工程每次建议最多 3 次模型请求、4 个工具调用，每个响应最多请求 2 个工具，不做失败自动重试。超时按每个请求计算，默认 15 秒，可配置 1–60 秒；多轮工程建议耗时可能累加。单次输入上下文超过 20000 字符时回退，每次输出限制为 1600 Token。
- 工程图 v2 在最后一次请求中停止提供工具，使用 JSON 对象模式形成建议，避免只查询不收尾。前面的查询顺序与是否提前结束仍由模型决定，最终结构、目录证据和人员编号校验不放宽。
- JSON 字段、字段类型、原文引用、有效人员编号和完成原因均需校验；截断、拒绝、越权字段或不合法输出不得标记为模型成功。
- 模型失败时返回受控原因，不把供应商响应正文、请求头、密钥或原始异常输出到页面和流程事件。
- 报修信息初审的实际模式、模型计量和提示词版本随流程事件保存。招商草稿与独立工程建议返回这些元数据，但本轮未新增持久化的模型审计表。
- 工程模型请求独立于建单事务，避免在 SQLite 写事务中等待模型。建单时已有的工程规则推荐仍会写入交接事件，不能据此认定工程模型已运行。
- 工程图基于本次数据库快照查询，不持有 Session 或业务写入工具。生成期间资料可能变化，正式分派时由原业务接口重新校验；建议不是分派凭据。工程轨迹与计量目前仅随响应返回，不支持刷新后恢复，也未配置原生图检查点。
- 旧 `/api/v1/agent/coordinate` 探索原型继续保持规则模式，不作为新千问入口；正式演示使用本说明中的受人工门禁约束的入口。
